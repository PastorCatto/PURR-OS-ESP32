# plan7: a Windows 10 Mobile style shell for PURR OS (adapting fbiego/windows-10-mobile-lvgl)

**Source of truth for this work.** Re-read after any context compaction. Update the Status table and the
Session log as work happens. Started 2026-10-26. Depends on plan6 (the app runtime): a UI is a client of the
runtime's event stream and dispatchers, so swapping the UI does not touch apps.

## Goal

Make a second shell for PURR OS from https://github.com/fbiego/windows-10-mobile-lvgl (MIT licence): a start
screen of live tiles, an app list, a lock screen, a status bar, a navigation bar, settings and a notification
panel, running on the T-Deck Plus, driven by the PURR app runtime, and usable by apps written once for any UI.

## What the reference project is (read from a shallow clone, 2025-06-05 commit `c62690f`)

- **LVGL 9.2** (`lvgl/lvgl@^9.2`). PURR OS **started on LVGL 8.3.11** and has since moved to **LVGL 9.2.2** (see the status table; the pin is in `PurrOS/main/idf_component.yml`).
- **Generated UI.** `src/ui/ui.c` (1659 lines) and `ui_common.c` (642 lines) are a SquareLine Studio export plus
  a small helper layer (`cm_*`: `cm_start_tile`, `cm_app_list`, `cm_settings_list`, `cm_create_switch`, ...).
  `squareline/W10M.spj` is the editable project.
- **Portrait 320x480.** The panel drivers are 320x480. The T-Deck Plus is **320x240 landscape**, so every
  screen needs a landscape layout, not a scale.
- **Apps are compiled in.** `hal/esp32/core/app_manager.cpp` registers apps by function pointer, and each app
  (`hal/esp32/apps/led`, `blog`, `fbiego`, `sample`) builds its own LVGL widgets directly. That is the opposite
  of PURR's signed, UI-agnostic `.cat` apps, so apps are **not** carried over; the shell is.
- **Arduino / PlatformIO.** The hardware layer (`hal/esp32`) uses Arduino, ESP32Time, LovyanGFX and its own Wi-Fi
  and HTTP code. None of that is reusable; PURR has its own.
- **Assets are 22 MB of C arrays** (`src/ui/images`, 58 files: wallpapers, tile art, icons). That cannot ship in a
  1.9 MB kernel slot. PURR keeps images on the `ui_assets` partition as raw RGB565 (`purrstrap uiassets build`).
- **Live tiles** are animated image panels (`liveTileVertical6_Animation`, `liveTileHorizontal5_Animation`)
  registered per tile, plus tile definitions in a static `start_tile_t tiles[]` table.

## The architecture (so this is a plug-in shell, not a fork of the OS)

```
 apps (.cat, UI-agnostic)        runtime (plan6)              shells (LVGL, in the UI service)
 console / ui / tile catcalls -> manager, events, dispatchers -> card stack  |  Windows 10 Mobile shell
```

- A **shell** is a client of the runtime: it subscribes to the event stream (`openapp`, `closeapp`, `focus`,
  `state`, `killed`) and calls dispatchers (`open`, `focus`, `close`, `background`). It never reaches into apps.
- **Tiles come from installed apps**, not a compiled table: name, accent colour and icon from the app (the
  manifest, once it carries them), tile size from `/etc/apps.conf` or the app's own request.
- **Live tiles are app-driven.** An app updates its tile through a `tile` catcall (title, text, image, "flip"
  animation), or an `event` the shell maps to its tile. The shell animates; the app only says what to show.
- **An app's window is a surface** the shell gives it (the `ui` catcall: widgets and a canvas, UI/SPEC.md). A
  console-only app gets a terminal surface. Status bar and nav bar belong to the shell and read the `system`
  catcall (clock, battery, network).
- Which shell is active is a setting (`/ui/mode.conf` already exists for text-versus-card); a shell failing to
  start falls back to the text shell, as today.

## Decisions needed

1. **LVGL 9.2 or back-port to 8.3.** The OS's own LVGL code is `purr_lvgl.c` (161 lines), `purr_ui_config.c`,
   `purr_ui_service.c` (1328 lines, mostly the card shell) and `purr_card_shell.c`. If the card stack is being
   retired, **upgrading the OS to LVGL 9.2** is the cleaner path: the reference code is native 9.x, 9.x has
   better draw performance, and only the small display and tick layer needs porting. Back-porting 2,300 lines of
   generated 9.x to 8.3 is possible but repeated for every upstream change. Recommendation: upgrade to 9.2, and
   keep the card shell building behind a flag until the new shell replaces it.
2. **Landscape layout.** Portrait Windows 10 Mobile on a 320x240 landscape screen needs a designed layout
   (start screen scrolling sideways in two rows of tiles, a slim status strip, the nav bar as three keys on the
   side). Does the owner want that, or a rotated portrait mode for boards that have a portrait panel?
3. **Assets.** Re-export wallpapers and tile art at 320x240, RGB565, to the `ui_assets` partition (about 150 KB per
   full-screen image). Which wallpapers and icon set to keep, and the licence of the art (the repository is MIT
   but the Windows logos and Lumia imagery are Microsoft's, so a shipped OS should use its own art).
4. **Attribution.** MIT needs the copyright and licence text kept. A `THIRD_PARTY.md` entry, and the licence
   file alongside any copied code.

## Sign-in and lock design (owner, 2026-10-26)

Two separate screens. **BFU (before first unlock)**: at boot the Windows 10 "Other user" sign-in screen is
the only thing reachable, and nothing is started for a user until it succeeds. **Lock screen (after first
unlock)**: the Windows 10 Mobile lock screen, reached by the Lock button in the control center (and later an
idle timeout); it is swipe-to-unlock and does not ask for the password again. That is what the owner asked for
and it is weaker than a locked phone: someone who picks up an unlocked-then-locked device only has to swipe.
A "require password to unlock" setting that reuses the sign-in screen would close that; not built.
First-time setup (no accounts yet) still uses the text prompt, then the shell starts already signed in.

`purr_login_try()` (login.c) is the non-blocking sign-in call with the text prompt's lockout rules (1, 2, 4 ...
60 s, kept in the account file). Timing note: an unknown user name returns faster than a wrong password for a
real one, as in the text prompt; worth hardening with a dummy hash.

## Theme and Settings design (owner, 2026-10-26)

The shell owns the look; apps get it. Theme struct (base, accent, on-accent by luminance) -> LVGL display
theme callback, so widgets an app creates through the `ui` catcall are W10M with no styling code. Apps may draw
on their own canvas but cannot restyle standard widgets. Settings is ported from the reference
(`cm_settings_list`, `cm_accent_color`, `cm_create_*`, `ui.c` settings pages) laid out for 320x240; pages are
wired to real things (backlight, idle timer, Wi-Fi, version/secure state, accounts); Devices and Privacy are
dimmed until the OS has them. Settings saved per user (text file, `accent=cobalt`, `base=dark`), sign-in uses
the system default. Order: struct -> helpers -> Settings main + Personalization -> System, About -> Network.

## Open issue: VM panic in the I2C interrupt (2026-10-26, found at the end of the bench test)

After ~23 min of use on the new build, tapping the Settings tile produced `LoadStorePIFAddrError` on core 0
(`PC 0x4037a183`, `A2 0x3c270004`) inside `i2c_ll_read_rxfifo` <- `i2c_isr_receive_handler` <-
`i2c_master_isr_handler_default`, interrupting the W5500 SPI task (`emac_w5500_task`). Nothing from the W10M,
theme, settings or account code is in the backtrace. Suspects: the I2C master receive buffer sits in PSRAM
(0x3c...) and an interrupt writes it; or the emulator's I2C model. Log: scratchpad `vm-serial-crash.log`.
To do: reproduce from a fresh boot with the same taps, find where the touch/keyboard driver's I2C receive
buffer is allocated, check `CONFIG_I2C_ISR_IRAM_SAFE` and any heap-in-PSRAM defaults.

## The lock screen becomes the sign-in screen (owner decisions, 2026-11-01; designed, nothing built)
Why: today's lock screen (`purr_w10m.c` ~1430-1590) is only a cover with "swipe up"; it asks for no credential and everything stays alive behind it, and there is no auto-lock (the only way to lock is the control center's Lock button).
- **Locked = the sign-in screen.** Delete the cover overlay, its drag handler and timer, and the lock wallpaper; the sign-in screen (avatar, name, password, PBKDF2 check) gets a locked mode.
- **What it shows:** once a user has signed in on this device, the screen shows that user's profile (avatar and name) and one password field, plus a "Sign in as another user" button that reveals the full name-and-password form. The last user is remembered device-wide. Before any user has ever signed in, the full form shows as today.
- **When it locks:** the Lock button, and automatically after the screen has been off for as long as the display timeout is set to (reading to confirm: with a 1 minute timeout the screen goes off at 1 minute and the device locks at 2). "Never" means never auto-lock.
- **Apps that are open stay frozen and hidden** (the lifecycle code); their windows are kept, so nothing unsaved is lost.
- **The shell's own UI is offloaded while locked** (start screen, app list, control center, notification panel, Settings): deleted on lock, rebuilt on unlock. Expected to free some tens of KB of internal RAM while locked (a guess, to measure).
- **Notifications while locked:** a message icon and a count, never the text.
- **Consequence to settle:** signing in as another user from the locked screen ends the first user's session (their apps are closed after saving state, with a warning), because the frozen apps belong to that user.
- **To think about:** failed-password back-off now that a password guards the lock; and that unlock rebuilds the UI (about a second, to measure). Protects the UI layer only: files at rest are not encrypted (per-user encryption keyed from the password is a separate project).

## Multitasking: the task view (owner, 2026-11-01; built in 1.0.14, run in the VM, not on a device)
**Swipe-up switched OFF, replaced by a task manager (owner, 2026-11-03; built in 1.0.16, not run on a device):** on the device the swipe fought the notification tray. `purr_w10m.c` no longer registers `purr_lvgl_set_edge_swipe`; the control center has a **Tasks** quick tile (fourth, so it shows while collapsed) that opens the **task manager** (`purr_w10m_tasks.c`, replacing the cards): a list of every running app with its state (in front, paused, in the background, service), the main memory it holds, and an **End** button; tapping a row brings the app to the front; the top line shows the fast (internal) RAM and main memory free, which is the number that limits how many apps can run (plan6). It redraws only when the set of apps changes, the numbers refresh every 2 s. It is a shell page like Settings, not a sideloaded app, because it needs the runtime's task list; `Home` still steps the app in front back without closing it. Not done: a sheet for the Settings/Portal pages (they are not runtime tasks), a keyboard shortcut.
There is no way to switch between running apps. Swiping up from the bottom edge opens the task view:
- A card for every running app (the foreground one and the frozen ones), about three across: a square with the app's icon or initial and its name, and a close button (X) in the corner. Tapping a card brings that app forward; the X closes it (its state is saved first); tapping outside, or a swipe down, goes back. The foreground app's card is marked.
- **Background services** (apps with no screen, such as the Store's companion) are not cards: a small indicator along the bottom lists them ("running in the background: ...").
- The swipe is detected in the touch read callback (press in the bottom ~16 px, then up by about 40 px) and then cancels the touch, so taps near the bottom edge of an app still work.
- Needs: a list of the running apps with their state from the runtime (id, name, kind, foreground, frozen, service), an asynchronous focus (like the existing asynchronous close) so the UI task never waits on an app, and a keyboard way to open it for devices without touch. Closed while the lock screen is up.
- Works with the app lifecycle already built: the frozen apps are the ones the cards show.

**Built (1.0.14).** `purr_w10m_tasks.c`; the swipe is detected in the touch read (`purr_lvgl.c`, with LVGL's own rotation transform), cancels the press and opens the view on the next tick. Cards for every running app that has a screen (initial, name, close button; the app in front has an accent outline), a **Home** button that sends the app in front back to the start screen without closing it (it is frozen, or keeps running if it may), the background services in one line along the bottom, a tap on empty space or a second swipe goes back, a tap on a card brings that app forward. Run in the VM with Beacon and Notes: both cards, Home, close, switch all work.
Not done: a keyboard way to open it (a bind on the runtime's `cycle` does the switching today); Settings and the Developer Portal are sheets of the shell, not runtime apps, so they have no card; rotating the screen closes the view.
**Also in 1.0.14: the trackball.** The board lists it (so Device Manager > Drivers > Get missing drivers fetches `trackball-gpio`), and the keypad reads it every 10 ms: a roll is an arrow key, a click is Enter, and a vertical roll scrolls the app window on screen unless a text field has focus. Not run on a unit: the pin directions are still unverified.

## Android shell build-out (owner go, 2026-11-04)
Goal: the Android-style (Froyo, QWERTY) shell with the same features, support and extensibility as the Windows-style shell, so an app written once runs the same in either UI (and in a third and fourth later). Owner decisions: the permission prompt draft is approved; Settings keeps the same set of settings, laid out the Android way; **developer things sit under Applications > Development** (the Froyo place); **Home = trackball long press** by default, a setting; the shell is chosen at build time.

**How it stays drop-in.** One official shell is compiled per image. Apps never see a shell: they call the `ui`, `tile`, `system`, `settings` and permission catcalls, and the OS draws the result. So the work is:
- *The contract.* `purr_w10m_priv.h` is the real shell contract (banner, busy, notifications, sheets, brightness, orientation, apps changed, the Settings, Portal and task manager entry points). The Android shell provides the same functions from its own files; the shared files (Settings, Developer Portal, task manager, permission prompt, the `ui` catcall windows, Store, widgets) are not copied. The five public entry points get neutral names in `purr_shell.h` (`purr_shell_start`, `..._set_orientation`, `..._lock`, `..._notify`, `..._refresh_apps`), forwarded at build time.
- *The skin.* One theme file, two skins, chosen by the same build option. New roles (button, list row, title bar) let the shared files say what a thing is and the skin say how it looks. The theme API and the `theme.*` settings keys stay, so `settings set theme.accent` still works (the Android default accent is amber, the Froyo orange).
- *The layout of Settings.* Settings is page builders plus a list of top-level entries. The Android shell gets its own list (Wireless and networks, Sound and display, Applications with Development inside, Accounts and sync, Date and time, Security, Storage and hardware, About phone) over the same page builders, so every setting that exists today still exists.
- *Nothing in the Windows-style shell is rewritten* beyond the call sites that move to the new roles.

**Chunks** (share of the whole, rough): 1 seam: Kconfig choice, build list, `purr_shell.h`, mode names (5 percent). 2 skin: new roles, Froyo styles, call sites moved to roles (10). 3 art: the Froyo icon pack converted for `ui_assets` (status, launcher, dock), `THIRD_PARTY.md` (7). 4 shell core: status strip with Froyo icons, notification icons, busy and banner, key strip, Home long press, orientation, brightness (13). 5 home and drawer: pages, dock, wallpaper, options menu, installed-app list, live tiles shown as badges (13). 6 shade: Ongoing and Notifications, clear, app notifications, the task manager entry (8). 7 lock and sign-in (8). 8 Settings layout and Development (10). 9 permission prompt, task manager, Portal and Store placement (6). 10 SDK and purrstrap shell option, docs, host tests, THIRD_PARTY (10). 11 compile fixes and the rest (10).

### 1.0.22: apps in PSRAM (owner, 2026-11-05)
**1.0.21 is frozen** (what the dev server holds; `signed21/` in the scratchpad is exactly that). New work goes into **1.0.22** (`signed22/`, scratchpad only, not on the server).
Owner's goal: ten apps open at once; an app at 29 KB free fast RAM would not open (it needed an 8 KB stack + 2 KB + the 24 KB reserve). Built, not run on a device:
- **App stacks, queues and semaphores in PSRAM** (`purr_catrt.c`: `xTaskCreateWithCaps`, `xQueueCreateWithCaps`, `xSemaphoreCreateBinaryWithCaps`, `APP_STACK_EXT_BYTES` 12 KB). An open app holds about 1 KB of fast RAM (`APP_INTERNAL_EXT`: its task record) instead of about 10. Self-delete uses `vTaskDeleteWithCaps(NULL)` (IDF 5.3 supports it). `apps.psram_stacks` = 0 is the way back to fast RAM stacks; no PSRAM for a stack falls back to one, with a log line.
- **The rule:** a task with a PSRAM stack must not call flash itself. All of an app's file and settings paths end in the raw partition calls of `purr_fs_flash.c`, `purr_cfgstore.c` and `purr_netrec.c`; those now go through `purr_io_partition_read/write/erase_range` (`purr_io.c`): a caller on an internal stack goes straight through, one on a PSRAM stack hands the access to the `flash_io` task (3 KB, priority 5) and waits. The file system's own logic stays on the app's stack. A flash call that is missed aborts loudly (IDF: stack in external RAM during a flash operation), naming the call.
- **Reserve 24 KB -> 16 KB** (`INTERNAL_RESERVE`). With ten apps at about 1 KB, ten fit in roughly 26 KB free above the reserve; a fresh boot here has about 29 KB.
- **To check on the device:** open apps until the Task Manager's fast RAM stops falling by about 1 KB each; the file listing, copy and the Store (its install jobs have their own tasks) in particular; no "stack in external RAM" abort; the `app:` tasks show "static stack"/PSRAM in the System services list.

## Accounts, Wi-Fi and settings lost after a failed read (2026-11-06; fixed in the kernels, run in host tests only)

**What happened.** The owner forced the kernel to load while trying to OTA, the OTA failed three times, the clean boot would not connect to Wi-Fi, and after a warm reset the device had only the default MEOW account (signed in on its own), no saved Wi-Fi, default display settings and no apps listed. **The data partition was not formatted**: the owner's profile folder and apps folder were still there; the account record, the Wi-Fi list and the settings were gone. (The first guess here, KittenOS formatting a damaged file system, was wrong for that reason.)

**Cause, found with a host test that injects a read failure.** In this littlefs, after one failed block read the **next clean read of an existing file returns "no such file"** (and only the read after that works): littlefs marks a block as cached before it reads it and does not undo that when the read fails, so its next lookups parse stale bytes. On top of that, three loaders took any failed read as "nothing saved yet": `purr_userstore_load` (accounts: it returned success with empty lists), `conf_load` in `purr_settings.c` (the settings) and `load_saved` in `purr_net_wifi.c` (Wi-Fi). With the "unattended setup" flag left by the automatic recovery, an empty account list made `first_time_setup()` create MEOW and `purr_login_persist()` save it over `/etc/passwd` and `/etc/shadow`; the settings and the Wi-Fi list were then saved over the same way by the next change. Why the read failed in the first place is not known (a flash read error during the glitchy boots, perhaps from the same heap damage as the touch panic above).

**Fixed (1.0.28).** `purr_fs.c`: a block read is retried three times below littlefs, and a persistent failure marks the file system poisoned, so the next operation remounts first (which clears every cache) and keeps trying until it works. `purr_fs_slurp()` returns 0 / 1 (the file does not exist) / -1 (it could not be read) and is used by the account store, the settings and the Wi-Fi list; `purr_fs_write_kept()` keeps the previous file as `.bak` on every save. The account store falls back to `.bak`, and returns `PURR_USERSTORE_READ_ERROR` if neither reads; `login.c` then never creates the default account, never saves (`purr_login_persist` refuses) and the boot-time login keeps retrying; settings and Wi-Fi refuse to save over a file that could not be read. Tests: `test_safeload.c` (45 checks, with read failures injected: absent vs unreadable, one transient failure absorbed, kept backups, the account store reading, falling back and refusing) and the existing file system tests (110 checks); all 35 host programs pass. **Not done:** the on-screen warning that says why data was replaced (`PURR_CFGF_DATA_RESET`, designed in the owner's words: a flag outside the data partition plus a reason record, shown at sign-in, as a notification and in About); the sign-in screens saying "the account list could not be read"; the OS version on the sign-in and About screens; making the dev server publish safe for a running OTA (files are replaced in place under fixed names: an OTA that overlaps a publish sees a size or hash mismatch). Not run on a device.

## UI packages: one pack per shell, in LittleFS (owner, 2026-11-06; designed, nothing built)

**Why.** Both shells load their pictures from one `ui_assets` partition through `purr_ui_assets_find`. A pack is one file, so whichever is published wins: the pack on the dev server (1.0.18, 149 KB, 50 pictures) has the Froyo art (`fr_*`, 21), the soft keys (`kb_*`) and the status icons (`st_*`) and **no Windows 10 Mobile pictures** (`wp_*`: system, devices, network, personalization, apps, account, time, privacy, about, settings...), so the Windows shell lost its icons. (The Windows icon sources are not in the repository; they came from `fbiego/windows-10-mobile-lvgl`, MIT, see `THIRD_PARTY.md`.)

**Decisions (owner).** Each UI is a self-contained package that can be swapped independently; **two separate packs, one for each shell**; the pack lives **in LittleFS**, not in a raw partition; about 3 to 5 MB at most; a user can make a shell and provide an icon pack.

**Design, phase 1 (assets).** `/ui/<shell>/pack.bin` (the format `purrstrap uiassets` writes today: header, directory, RGB565 data, CRC) and `/ui/<shell>/ui.conf` (name, author, licence, version). `purr_ui_assets_init(shell)` reads the shell's own pack (into PSRAM, or each picture on demand) and falls back to the old raw partition during the move. Release components `ui-w10m` and `ui-android` (instead of one `uiassets`); the recovery's stage 2 installs the one for the shell it set up; an icon pack is the same file with a different manifest, signed by its maker like a repository. A `tools/ui/w10m_pack.py` rebuilds the Windows pack from upstream, next to `froyo_pack.py`. **Space:** the root file system is about 6 MB; the icons are small (50 pictures in 149 KB), so a pack in LittleFS is fine, and the 3 to 5 MB figure only applies with big wallpapers (those can go on the SD card). The raw 5 MB partition could later be merged into LittleFS, which changes the partition table and so needs a cable flash.
**Phase 2 (code).** A shell's code as a signed loadable module (like apps and drivers, loaded to PSRAM), which needs the LVGL and OS functions exported as a versioned table (a shell ABI), and would also free kernel space (the two shells today are compiled in, one per image). Not designed in detail.

**Release and the switch (owner, 2026-11-06).** The UI packages and the per-shell packs come in **1.0.29** (1.0.28 gets the data fix, the OTA move and the safety items above). The owner also wants a **setting in Settings to switch the UI with a toggle**: it lists what is available (what is installed, and what the hub offers: "pull what's available") and switches the start screen between them. **What decides how instant that is:** today each image compiles in exactly one shell (Kconfig choice `PURR_OFFICIAL_SHELL`, the kernel slot has about 70 KB free), so there is nothing to switch to inside one image. Two ways: **(A, fits today's design)** the setting offers each shell as a release channel entry; choosing one has the recovery loader install that shell's kernel build (about 2 MB, verified like any OTA) and restart: minutes, not a toggle, and the per-shell pack arrives with it; **(B, the real toggle)** phase 2: shells as signed loadable modules, so switching is stopping one shell module and starting another on the UI task, with their packs in LittleFS; it needs the shell ABI. Recommendation: A in 1.0.29 with the packs, B after it. The owner decides.

**Themes from the Store, three at a time (owner, 2026-11-06; designed for 1.0.29).** A user can install a custom theme from the App Store; every installed theme shows up in Settings (the UI list), choosing one takes effect **on restart**, and **only 2 to 3 themes are kept on the device at a time** (space); more can live on the SD card and be swapped in. Written down as:
- **A theme is assets plus settings, not code.** A pack (the `purrstrap uiassets` format: pictures, wallpapers) and a `theme.conf` (name, author, licence, version, the shell it is for, accent and light or dark base). It runs no code, so a community theme is acceptable on the same trust tiers as a repository; **a font in a theme is not**, because the font renderer says it must not be given untrusted files (docs/21-fonts.md): fonts only from an official or trusted source.
- **Layered lookup.** `purr_ui_assets_find()` asks the active theme's pack first and the shell's built-in default pack second, by name (`wp_*` for the Windows shell, `fr_*`, `kb_*`, `st_*` for the Android one). A theme that only changes the wallpaper and a few icons still works; the shell always has its default pack, which is part of the OS and not counted in the three.
- **Where.** `/ui/themes/<id>/` in LittleFS (three slots, a setting `ui.theme_slots`, default 3) and `<SD>/ui/themes/<id>/` (any number). The choice is `/ui/active.conf`, read at start before the assets are loaded; **the switch is applied at the next restart** and Settings says so.
- **Swapping.** Choosing a theme that is only on the SD card **copies it into a slot** (the card can then be removed), asking which installed theme to replace when the three slots are full (the least recently used is suggested). Removing a theme frees its slot. If the active theme cannot be loaded at start (a damaged file, a missing card) the shell starts with its default pack and shows a notice naming the theme.
- **The Store.** A new item type `theme` in the repository format (`Repositories/SPEC.md` has app, asset and extra), with the shell it is for, a size, a licence shown before installing and a preview picture; the Store's companion installs it into a slot or the SD card, and Settings lists whatever is there. Installing a fourth theme asks which of the three to replace.
- **Open (owner):** whether a theme may also carry wallpapers larger than a slot (on the SD card only), and sounds.

**A whole UI can replace the shell (owner, 2026-11-06; decision: option B; designed, nothing built).** Someone who rebuilds a complete UI can publish it as a **shell package** that takes the place of the shell **if it meets the criteria and is signed off by its developer with a signature and a key**. This settles the A or B question above: shells become signed loadable modules; the earlier "kernel build per shell" idea is dropped. Themes (assets only, previous section) stay the light way to change the look. Proposed rules, for the owner to confirm:
1. **A shell package** is one signed container: the shell's code (relocatable, loaded to PSRAM the way apps and drivers are), its own asset pack, and a manifest (name, version, author, licence, the **shell ABI** version it was built against, the `ui` catcall and OS versions it needs, the boards it supports, its memory budget).
2. **The shell ABI**: the LVGL functions and the OS services a shell may call (sign-in, settings, notifications, apps, power, Wi-Fi status...), as one versioned table; anything else is an unresolved import and the package is refused. `purr shell check` in the SDK runs the same checks on the maker's computer; `purr new shell` starts a project.
3. **Install-time criteria:** a valid signature from a key the device trusts for UI packages; the ABI version is one this OS supports; size and memory limits; the required entry points exist (init, start, stop, event); only ABI imports; the usual module checks (relocations, bounds, hash).
4. **Trust:** official (signed by the project: may be the default), or **community** (the developer's own key, which the owner confirms by its fingerprint like a repository; the screen says plainly that a UI sees every key typed, including passwords). **A shell handles sign-in, so the signature is the only protection: the device owner decides whose keys count, and a device that is dev-locked or enterprise-managed accepts only project-endorsed shells** (a locked device is never weakened on the device).
5. **It can never lock the owner out.** One shell stays compiled in as the **fallback**; a custom shell is chosen at the next restart, and if it fails to start, crashes, or the boot-failure count rises, the device goes back to the previous or built-in shell on its own, quarantines the package and says so (the data-reset style notice).
6. **Slots:** full UI packages and themes share the same few slots in LittleFS (three by default) and more can live on the SD card.
**Order.** 1.0.29: the per-shell packs in LittleFS and themes (assets). Then the shell ABI and the first loadable shell (the Windows shell converted, with the fallback shell staying compiled in): the biggest item, because today's shells call kernel internals directly (login, settings, update, power, notifications) and each of those has to become part of the ABI.

**Owner's answers on the shell rules (2026-11-06), replacing rules 4 and 6 above.**
- **Whose keys count.** A shell is accepted when it is signed by a key **in that device's own key bag** with the right role; the device owner is whoever's keys are in the bag. On a project device that means project keys: **a locked device takes only project-endorsed shells, and anything signed with an extra key of the owner's own is for locked devices only by endorsement.** Someone who builds their own chain (their bootloader, their images, their keys: the vendor overlay of plan3) **keeps a normal lock without developer mode and trusts their own key, not the project's**, so a shell they sign with that key loads on their device. That is how the OS supports more than one key root without relying on the project: no new trust concept, the key bag already decides. The screen still warns that a shell sees every key typed.
- **No slots for UIs.** A shell package is a file, `/ui/shells/<id>.cat` in **LittleFS**, loaded the way apps, drivers and system modules already are (`load_relocatable_file()` in `commands.c`: read from LittleFS, verify the signature, relocate, run from PSRAM), so the only limit is free space. What has to change: the page budget (one 64 KB MMU page per module today; a shell needs several) and the read buffer. A shell kept on the SD card is copied into LittleFS to run (the card can then be removed). **The three-slot limit stays for themes only** (assets chosen from the Store).

**The shell's own page budget and read buffer (owner, 2026-11-06).** The module loader takes a page budget and a read buffer per kind (`PURR_MODULE_LOAD_MAX_PAGES` is 1 and `PURR_KERNELMOD_LOAD_MAX_PAGES` is 1 in `commands.c`, with app and driver caps of their own). The shell gets **its own pair**: `PURR_SHELL_LOAD_MAX_PAGES` (8 pages of 64 KB, so up to 512 KB of code, raised when a shell needs more) and `PURR_SHELL_READ_CAP` (1 MB, a PSRAM buffer that exists only while the package is read and relocated and is freed right after, as `load_relocatable_image()` already frees its buffer). Nothing else's budget changes, so a large shell cannot starve apps or drivers of pages. Part of the shell work after 1.0.29.
